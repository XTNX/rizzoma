# Промпт для разработки: RIZZOMA — подготовка к стартовой бете

> ТЗ на следующий этап после [`app-redesign-prompt.md`](app-redesign-prompt.md) (уже реализован,
> см. `README.md`). Режим по `references/redesign-protocol.md` — **Extension**: дерево узлов,
> движок сцены, схема БД и бренд-токены не переизобретаются, добавляются ограниченные новые
> элементы поверх существующего словаря. Не превращай точечную задачу в очередной overhaul.

## 0. Роль, режим, какие скиллы использовать по ходу

Работа разбита на слои — веди каждый профильным инструментом, не одним проходом:

| Слой | Скилл/подход |
|---|---|
| Контракт `/api/purchase`, схема тикетов, вебхук провайдера | `api-designer` — сначала зафиксировать контракт, потом кодить |
| Бэкенд-часть (вебхук оплаты, allowlist админки, `bot/`) + фронт-часть, которая от него зависит | `fullstack-guardian` — оплата и права доступа целиком, не только UI |
| Туман, полосатая текстура на overscroll, редизайн формы оплаты | `web-design-engineer` — это визуальная/motion-работа поверх уже заданного языка (`brand-spec.md`), не с нуля |
| Токены, вебхуки, allowlist, initData-проверки | `security-review` — прогнать перед тем, как бета уйдёт живым тестерам |
| Автотесты (юнит + e2e) | `test-master` |

Перед стартом зафиксируй план по протоколу (`redesign-protocol.md#6`):

```text
Mode: Extension
Preserve: buildWedge/makeScene, TIERS (числа порогов не менять), BRANCHES, схема localStorage,
          контракт /api/visit и /api/friends, дизайн-токены brand-spec.md
Improve: копирайт, форма чекаута (комбинации билета), безопасность admin-доступа
Add: слой тумана + полосатая текстура overscroll, реальный платёжный провайдер,
     инвайты через Bot API напрямую, бета-админка с allowlist, автотесты
Protected contracts: числа в TIERS, ключи localStorage/CloudStorage, HMAC-валидация initData
Highest-risk change: приём настоящих денег и настоящих initData вместо localStorage-имитации
Rollback: текущий index.html/bot.js остаются в git-истории, откат — предыдущий коммит
```

## 1. Что входит в этот этап

Бета — не весь продукт, а урезанный, проверяемый срез:

1. **Туман войны** — на дереве видна и доступна только часть скиллов, остальное визуально
   закрыто, но не удалено из сцены.
2. **Открытая часть = только проходки** — без мерча, с одной VIP-привилегией.
3. **Платёжная форма** — реальный выбор состава билета (одиночный/парный/тройной ×
   обычный/VIP), реальный платёжный провайдер вместо клиентской имитации карты.
4. **Инвайты напрямую через Telegram Bot API** — не localStorage-мок, а сервер + initData,
   как уже частично сделано в `bot/`, но теперь это единственный источник правды для беты.
5. **Копирайт** — переписан по образцу реальных каналов движения, без абстрактной «ритуальной»
   прозы.
6. **Автотесты + скрытая бета-админка** — для управления самим тестом, отдельно от текущей
   QA-панели.

## 2. Туман войны

### 2.1 Что открыто, что закрыто

Открытая часть = только про доступ на площадку, без мерча, ровно одна VIP-ветка:

| Скилл | Порог | Ветвь | Статус в бете |
|---|---|---|---|
| ПРОБИТИЕ | 1 | ВОЛЯ | открыт |
| ПРОХОД | 3 | ВОЛЯ | открыт |
| ОБХОД | 10 | ВОЛЯ | открыт |
| ГЛУБИНА | 15 | РАЗУМ | открыт — единственная VIP-привилегия беты |
| КАПСУЛА, РЕЛИКТ, ТОТЕМ | 5/25/100 | ТЕЛО (мерч) | под туманом |
| КОНТУР, РЕЗИДЕНТ, ВЕЧНАЯ ВЕТВЬ | 40/60/80 | РАЗУМ (кроме ГЛУБИНЫ) | под туманом |

Технически — новая константа рядом с `TIERS`/`BRANCHES` (`index.html:755` и `:772`),
например `BETA_OPEN = [0,1,3,4]` (индексы `TIERS`). **Не удалять и не менять сами `TIERS`/
`BRANCHES`** — это разметка, кто попадает под туман, а не новая экономика.

### 2.2 Важно: два разных «закрыто» — не перепутать в UI

- **«Не хватает рефералов»** — реальный прогресс внутри открытой части (условие `n` из `TIERS`).
  Копирайт: «ещё N рефералов» (как сейчас).
- **«Вне беты»** — весь раздел не участвует в тесте независимо от числа рефералов. Это **другой
  текст и другой визуал** (туман, не полупрозрачный узел): тестер не должен подумать, что ему
  просто не хватает рефералов до мерча — он должен понять, что это будущий контент.

### 2.3 Визуал тумана

- Геометрия сети рисуется как есть (`buildWedge`/`makeScene`, `index.html:1181`+) — узлы под
  туманом физически существуют на тех же вершинах клина, не скрываются из данных. Поверх
  соответствующих угловых секторов (группы `ТЕЛО` и части `РАЗУМ` вне `ГЛУБИНЫ`) рисуется
  дополнительный слой: затемнение + понижение контраста/десатурация, без обводки-заглушки —
  ощущение «карта есть, но не вся исследована», а не «эта часть удалена».
- Ядро (логотип) и открытые узлы остаются чёткими на любом зуме.
- Тач по узлу под туманом: короткая обратная связь («вне беты»), не открывает окно скилла,
  не реагирует на удержание.

### 2.4 Полосатая текстура на overscroll

В сцене уже есть резиновый overscroll на границах поля (`index.html:1001`, `:1155`, `:1670`) —
драг тормозится за кромкой и возвращается при отпускании. Расширить: если направление
overscroll ведёт **в сторону туманного сектора**, поверх резинового оттяга появляется
диагональная полосатая текстура (по образцу сигнальной ленты — чередующиеся полосы под 45°,
цвета из токенов, без нового цвета мимо палитры — например `--ink`/`--accent-secondary`), сила
непрозрачности растёт с глубиной оттяга и гаснет при возврате. Реализация — `repeating-linear-
gradient` на CSS-слое поверх канвы либо `Path2D`-штриховка в той же системе координат, что и
сцена (не отдельный DOM-элемент не в масштабе). Хаптика на упоре в туман — `impactOccurred('rigid')`,
отличная от обычного мягкого upscroll-предела.

## 3. Платёжная форма: состав билета

Сейчас `TICKETS` (`index.html:781`) — плоский список трёх тарифов по волнам продаж
(Early/Regular/На входе), без деления по составу и классу. Для беты нужна двумерная
комбинация:

| Ось | Значения |
|---|---|
| Состав | одиночный (1 проходка) · парный (2) · тройной (3) |
| Класс | обычный · VIP |

Итого 6 SKU. Технически — не плодить 6 отдельных объектов вручную, а держать матрицу цен
(`base` по классу × коэффициент по составу, либо явная сетка 3×2) и рендерить выбор как два
сегмент-контрола в `renderCheckout()` (`index.html:2051`) вместо/вместе с текущим списком
`TICKETS`. Итоговая цена по-прежнему проходит через `effPrice()` (`index.html:790`) — тирная
скидка/бесплатный вход по рефералам применяется к выбранной комбинации, а не только к
дефолтному тарифу. VIP-класс в форме — это **прямая покупка**, отдельная от заработанной
рефералами `ГЛУБИНЫ` (бесплатный/льготный VIP по дереву). В UI явно разведи эти два пути к
VIP, не дай тестеру решить, что это одно и то же.

Волны продаж (Early/Regular/На входе) можно оставить как отдельное измерение или свернуть —
на усмотрение исполнителя, но не в ущерб паре «состав × класс», которая обязательна.

## 4. Платёжная система

### 4.1 Официальные доки (обязательное чтение перед реализацией)

- [Bot Payments API](https://core.telegram.org/bots/payments) — общий контракт `sendInvoice`/
  `successful_payment` для физических товаров и услуг (билет на мероприятие — этот случай).
- [Stars — Bot Payments API для цифровых товаров](https://core.telegram.org/bots/payments-stars) —
  **не наш случай**: Stars обязательны только для цифровых/внутриапповых товаров ради политик
  App Store/Google Play. Билет на реальное событие — физическая услуга, Stars не требуются,
  разрешён внешний провайдер.
- [Telegram Mini Apps / WebApp JS API](https://core.telegram.org/bots/webapps) — `WebApp.
  openInvoice()`, `MainButton`, `HapticFeedback` (уже используются в проекте, см. `README.md`).
- BotFather: `https://t.me/BotFather` → `/mybots` → выбрать бота → **Payments** → подключить
  провайдера → получить `provider_token`, вставить в `sendInvoice` на бэкенде (аналогично
  тому, как `BOT_TOKEN` сейчас живёт только в `bot/.env`, см. `README.md` → «Секреты»).

### 4.2 Варианты провайдера при обороте до ~100 000 ₽/мес

Оценка на момент подготовки промпта — **перепроверить актуальные тарифы в личном кабинете
перед подключением**, они меняются чаще, чем этот документ.

| Провайдер | Подходит для | Комиссия (ориентир) | Плюс для этого оборота | Ссылки |
|---|---|---|---|---|
| **ЮKassa** — рекомендация №1 | самозанятый/ИП | карты от 2,8% · СБП от 0,4% (снижённые тарифы действуют по акции до 01.12.2026 для новых подключений с сайта) | нативная интеграция через BotFather Payments, без абонплаты, онлайн-подключение без визита в офис | [yookassa.ru](https://yookassa.ru/) · [для самозанятых](https://yookassa.ru/platezhi-dlya-samozanyatyh/) · [тарифы](https://yookassa.ru/fees/) |
| **Robokassa** — запасной вариант | самозанятый/ИП | без абонплаты, автоотправка чеков в тариф включена | отдельный телеграм-бот подключения (`@RobokassaShopBot`) — быстрый онлайн-онбординг, вторая точка входа, если ЮKassa отклонит категорию (ночные мероприятия 18+ иногда попадают под ручную проверку риска у части эквайеров — иметь запасного провайдера разумно) | [robokassa.com/solutions/business/samozanyatye](https://robokassa.com/solutions/business/samozanyatye/) |
| CloudPayments / Prodamus — не приоритет для этого оборота | бизнес с подписками/рассрочкой | обычно дороже входной порог/абонплата | избыточны для разового билета на 100к оборота; держать в уме, если позже появятся подписки на будущие события | [cloudpayments.ru](https://cloudpayments.ru/) · [гайд по телеграм-боту](https://cloudpayments.ru/blog/how-to-create-a-telegram-payment-bot/) |

**Практическая рекомендация**: подключить ЮKassa как основной провайдер через BotFather
(нативный `sendInvoice`/`openInvoice`, знакомый Telegram-пользователю UX «оплатить кнопкой»),
по умолчанию предлагать оплату через СБП (самая низкая комиссия на этом обороте), карту —
как запасной способ. Зарегистрировать Robokassa параллельно, но не подключать в проде — как
план Б, если ЮKassa попросит доп. проверку по категории мероприятия.

Условие для обоих вариантов — статус самозанятого (лимит дохода 2,4 млн ₽/год, 100к/мес
укладывается с запасом) или ИП. Если статус ещё не оформлен — это отдельный шаг до
подключения провайдера, не после.

### 4.3 Схема интеграции с текущим кодом

- Заменить клиентскую Луна-имитацию в `renderForm()` (`index.html:2088`) на `WebApp.
  openInvoice()` с ссылкой на инвойс, который создаёт бэкенд (`sendInvoice` через `provider_
  token` из BotFather).
- `/api/purchase` (`bot/bot.js`, контракт в `README.md`) перестаёт быть эндпоинтом, которому
  верит клиент напрямую — начисление проходки происходит **по вебхуку `successful_payment`**
  от Telegram/провайдера на бэкенд, клиент только инициирует инвойс и получает статус.
  Тестовые карты (`4242…`/`4000…0002`) остаются доступны только в браузерном fallback-режиме
  вне Telegram — как явно помеченная демо-имитация для случая без Mini App.
- Секреты платежа (`provider_token`, ключи вебхука) — только в переменных окружения бэкенда,
  по той же схеме, что `BOT_TOKEN` сейчас (`bot/.env`, `.gitignore`, никогда в статике).

## 5. Инвайты напрямую через Telegram API

### 5.1 Что меняется

Сейчас реферальный граф в проде уже строится ботом (`bot/bot.js`: `/start`, `/api/visit`,
`/api/friends`, HMAC-валидация `initData`) — это и есть «напрямую через Telegram API».
Для беты убрать оставшуюся localStorage-имитацию (`rizzoma_mock_db`) как источник правды
там, где `apiBase` задан: `/api/friends` и статус `paid` должны читаться с бэкенда, а
localStorage — только офлайн-кэш последнего ответа, не единственное хранилище.

### 5.2 Безопасная публикация токена

Токен бота (и теперь ещё `provider_token`) — критичный секрет, схема не меняется, только
расширяется на второй секрет:

- никогда не в статике/репозитории — только `bot/.env` локально (закрыт `.gitignore`) и
  переменные окружения хостинга бэкенда (Render/Railway/Fly.io/свой сервер) в бою;
- доступ к панели хостинга — только с аккаунта, который реально управляет ботом;
- если токен засветился — `/revoke` у @BotFather → новый `/token`, то же самое для
  `provider_token` через личный кабинет провайдера;
- для CI/автотестов (см. §7) — тестовый токен кладётся в GitHub Actions Secrets
  (`Settings → Secrets and variables → Actions`), не в файлы репозитория и не в логи джобы.

### 5.3 Тестирование с двумя личными аккаунтами Telegram

Два аккаунта — не проблема, а готовая пара «хост + тестер» для сквозной проверки без
привлечения посторонних людей:

1. **Завести второго бота** через BotFather — например `@rizzoma_beta_bot`, отдельный от
   продового `@rizzoma_..._bot` из `config.js`. Отдельный `BOT_TOKEN`, отдельный `APP_URL`
   (стейджинг-деплой/ветка), отдельный `provider_token` **в тестовом режиме** провайдера —
   бета никогда не бьёт по боевому счёту эквайринга.
2. **Аккаунт №1** (тот, что администрирует ботов в BotFather) — заносится по Telegram user
   id в allowlist бета-админки (см. §7.2). Это «хост»: генерирует реферальную ссылку,
   раздаёт тестерам.
3. **Аккаунт №2** — чистый «тестер»: открывает ссылку от аккаунта №1 в `@rizzoma_beta_bot`,
   проходит путь целиком (дерево → узел → покупка тестовым/сандбокс-платежом → появление
   в `/api/friends` у аккаунта №1). Так проверяется весь маршрут инвайта между двумя
   реальными Telegram id ещё до подключения живых тестеров.
4. Продовый бот из `config.js` не трогается на время беты — переключение на боевой провод
   происходит отдельным шагом после того, как сценарий из п.3 пройден чисто.

## 6. Копирайт — переписать полностью

### 6.1 Ориентир — реальные каналы, не абстракция

Разбор трёх каналов ([@rizzoma26](https://t.me/rizzoma26), [@kontrkult](https://t.me/kontrkult),
[@kpacu8o](https://t.me/kpacu8o)) — общие правила, которые нужно применить ко всему
пользовательскому тексту в приложении:

- **Факты вперёд, не образы.** `@rizzoma26` не пишет «портал открывается» — пишет «Осталось
  30 билетов», «Остался 1 день и 10 билетов», координаты точкой, дата цифрами. Приложение
  должно говорить то же: числа, сроки, статус — первым делом.
- **Короткие фрагменты, не сложноподчинённые предложения.** Строка — это одна мысль, не абзац.
- **Списки и нумерация вместо описательной прозы** — там, где сейчас в проекте связный текст
  (инструкции, условия), заменить на пункты, как в правилах входа у `@rizzoma26` или FAQ-блоке
  `@kpacu8o` (вопрос — тире — короткий ответ: «Тариф поменяет стоимость? — Нет!»).
  Скопировать именно эту Q&A-форму для FAQ-подсказок в приложении.
  (⚠ безопасность: правила `@rizzoma26` — реальный юридический/охранный текст конкретной
  площадки; не копировать его дословно как «наши правила», использовать только как образец
  *формы*, содержание — своё и проверенное юристом/организатором.)
- **Emoji — ритм, не украшение.** `@kontrkult` держит один-два символа как визуальный
  разделитель (🗝, ⬛️), не эмоциональную подпись к каждой фразе. Если в приложении есть
  emoji — так же: скупо, как метка состояния/раздела, не «весёлый» декор.
  Дефис/двойная черта как знак-разделитель («децентрализация ||») можно взять как приём для
  коротких системных строк дерева/тумана.
- **CTA — одно-два слова.** «купить билет», «tickets», «Узнать больше» — не длинные
  побуждающие фразы.
- **Никакой «улыбчивой» маркетинговой интонации и никакой избыточной мистики.** Текущий
  «ритуальный» регистр приложения (см. `app-redesign-prompt.md#11`) был направлением для
  первой версии; для беты — заземлить его этой конкретикой, не выбрасывать бренд целиком,
  а перестать быть абстрактным.

### 6.2 Было → стало (конкретные примеры по текущим строкам)

| Где | Сейчас | Переписать в духе каналов |
|---|---|---|
| `TIERS[1].line`, `index.html:757` | «Допуск обнуляется в цене» | «3 реферала = билет бесплатно» |
| `TIERS[3].line`, `index.html:759` | «Очередь перестаёт существовать» | «10 рефералов = без очереди» |
| Онбординг-ритуал, `README.md` | «касание разворачивает сеть кольцо за кольцом, по ней прокатывается импульс готовности» | короткая факт-строка о том, что происходит и что делать: «Разверни сеть. Дальше — сама.» и т.п. — без «импульса готовности» |
| Дисклеймер тумана (новый) | — | «Вне беты» / «Скоро», без пояснительных абзацев |

Это не финальные формулировки — исполнитель проходит этим методом по всем оставшимся
пользовательским строкам приложения (не по техническим/админским — там язык остаётся
функциональным). Юридически значимый текст (реальные адреса, возрастные ограничения,
условия провайдера) — не сочинять по мотивам чужого канала, брать только реальные,
согласованные данные события.

## 7. Автотестирование

### 7.1 Что покрывать

- **Юнит-тесты чистых функций**: `effPrice()`, новая матрица цен «состав × класс» (§3),
  `tierIndex()`/`tierName()`, деление `BETA_OPEN` vs остальное. Без сборки в проекте нет —
  достаточно встроенного `node:test` (Node 18+), не тянуть jest ради нескольких функций.
- **E2E-сценарии** (Playwright — headless-браузер без правки архитектуры проекта):
  - приёмочный сценарий из `README.md` («открыть `?ref=КОД1` → оплата → счётчик КОД1 +1»),
    адаптированный под реальный провайдер в тестовом режиме;
  - туман: узел вне `BETA_OPEN` не реагирует на долгое нажатие, тач показывает «вне беты»,
    не «не хватает N»;
  - overscroll в сторону тумана показывает полосатую текстуру и возвращается резинкой;
  - комбинации чекаута: все 6 SKU (состав × класс) дают корректную цену с учётом `effPrice()`;
  - двойной сабмит оплаты не создаёт вторую запись (уже описанный инвариант, перенести на
    новый флоу);
  - **негативный тест допуска**: аккаунт не из allowlist не видит бета-админку ни по одному
    из входов (см. §8.2) — это тест на security-регресс, не просто UI.
- CI — `.github/workflows/ci.yml` в уже существующем публичном репозитории (`XTNX/rizzoma`,
  см. предыдущий этап), прогон на каждый push/PR: `node --test` + `playwright test`.
  Секрет тестового `BOT_TOKEN`/`provider_token` — через GitHub Actions Secrets (§5.2), не в
  файле workflow.

## 8. Бета-админка (скрытая от тестеров)

### 8.1 Чем отличается от текущей QA-панели

Текущая панель (`?admin=1`/`?devpanel=1`/5 тапов, `index.html:2471`) — инструмент разработчика
для прогона механики, гейтится только обфускацией (см. предупреждение в самой панели: «не
для боевого использования»). Для беты это уже недостаточно: нужна панель именно **управления
тестом**, доступ к которой не должен подбираться простым знанием url-параметра.

### 8.2 Доступ — allowlist по Telegram id, не по трюку

- Список Telegram user id (аккаунт №1 из §5.3, плюс кто ещё администрирует бету) — в
  переменной окружения бэкенда (`ADMIN_TG_IDS`), сверяется на сервере через уже существующую
  `validateInitData()` (`bot/bot.js`) — то есть попытка открыть админку без валидного initData
  от id из списка получает `401`, а не просто скрытую кнопку.
- Существующие клиентские входы (`?admin=1`, 5 тапов) остаются как есть **только** для
  локальной разработки/бразуерного QA вне Telegram — но всё, что реально управляет бета-
  тестом (см. §8.3), должно идти через серверную проверку, а не только через клиентский флаг.

### 8.3 Что должна уметь бета-админка

- **Список тестеров**: кто из приглашённых аккаунт-2-уровня дошёл до какого шага (открыл
  приложение / открыл узел / оплатил) — витрина воронки, не сырой JSON.
- **Точечное управление туманом**: включить/выключить `BETA_OPEN` для конкретного узла на
  лету (без деплоя) — проверить, как быстро можно расширить открытую часть по ходу теста.
- **Ручная выдача/отзыв доступа тестера** — на случай, если кого-то нужно исключить из беты
  без правки кода.
- **Журнал платежей теста**: список тестовых транзакций (провайдер в sandbox-режиме),
  статус вебхука `successful_payment` — видно, дошло ли начисление до бэкенда, а не только
  до клиента.
- **Экспорт логов** (open/claim/purchase, уже частично есть в QA-панели, §README «QA/админка»)
  — расширить на данные с бэкенда, не только localStorage.
- Явная плашка отличия от QA-панели: «БЕТА-АДМИНКА · управляет живым тестом, не демо-БД».

## 9. Технические ограничения

- Правки — расширение существующего `index.html`/`bot/bot.js`/`config.js`, без смены
  архитектуры (статика + опциональный Node-бэкенд, без сборщика/фреймворка).
- Дизайн-токены не меняются (`brand-spec.md`) — туман и полосатая текстура собираются из
  существующей палитры, не вводят новый цвет.
- Схема localStorage (`rizzoma_mock_db`/`rizzoma_me`/`rizzoma_attribution`/`rizzoma_claims`)
  остаётся резервным/офлайн-слоем, не удаляется — просто перестаёт быть единственным
  источником правды там, где есть бэкенд.
- `prefers-reduced-motion`/`?reduce=1` — туман и полосатая текстура должны иметь статичный
  эквивалент (сплошная заливка/бордер вместо анимированной штриховки), функциональность
  (различение «нет рефералов» vs «вне беты») сохраняется и в статичном режиме.

## 10. Критерии приёмки

1. Узлы вне `BETA_OPEN` видны на сцене (геометрия не вырезана), но визуально закрыты туманом,
   не реагируют на удержание, тач даёт текст «вне беты», отличимый от «не хватает N».
2. Overscroll в сторону тумана показывает полосатую текстуру, пропорциональную глубине оттяга,
   и резинкой возвращается — не залипает.
3. Открытая часть дерева = ровно ВОЛЯ (ПРОБИТИЕ/ПРОХОД/ОБХОД) + ГЛУБИНА, без единого узла
   ТЕЛО (мерч) и без остальных VIP/пожизненных скиллов РАЗУМ.
4. Форма чекаута даёт все 6 комбинаций «состав × класс» с ценой, учитывающей `effPrice()`.
5. Оплата идёт через `WebApp.openInvoice()` и реальный (тестовый режим) `provider_token`,
   начисление проходки — по вебхуку `successful_payment` на бэкенде, не по ответу клиента.
6. Полный сценарий §5.3 (аккаунт-хост приглашает аккаунт-тестера, тестер платит в sandbox,
   у хоста в `/api/friends` появляется запись) проходит на отдельном стейджинг-боте, не
   трогая продовый бот/провод из `config.js`.
7. Токены (`BOT_TOKEN`, `provider_token`) нигде не попадают в статику/репозиторий/логи CI —
   только переменные окружения бэкенда и GitHub Actions Secrets.
8. Бета-админка недоступна для Telegram id вне allowlist даже при попытке зайти по
   `?admin=1`/пятью тапами — есть негативный автотест на это (§7.1).
9. Автотесты (юнит + Playwright) зелёные в CI на пуше; сценарии покрывают тьман, комбинации
   чекаута, двойной сабмит, негативный тест допуска.
10. Пользовательский текст (онбординг, подписи скиллов открытой части, FAQ-подсказки, тексты
    тумана) переписан по правилам §6 — короткие факт-строки/списки/Q&A вместо абстрактной
    ритуальной прозы; юридически значимый контент — реальный, не сочинённый по мотивам чужих
    каналов.
