# Промпт для разработки: интеграция Telegram API — баллы за активность в t.me/rizzoma26

> ТЗ на новый, независимый модуль поверх уже реализованной беты
> (см. [`beta-launch-prompt.md`](beta-launch-prompt.md), `README.md`). Режим по
> `references/redesign-protocol.md` — **Extension**: существующая механика рефералов
> и дерева скиллов (`economy.js`, `TIERS`/`BRANCHES`) не трогается вообще, добавляется
> параллельная система баллов за активность в Telegram-канале. Файл написан по итогам
> предварительной проверки — то, что помечено «выяснено», проверено инструментами
> в ходе подготовки промпта, а не предположение.

## 0. Роль, режим, какие скиллы использовать

| Слой | Скилл/подход |
|---|---|
| Контракт нового эндпоинта, форма события, форма баллов | `api-designer` — сначала зафиксировать, что именно сервер отдаёт клиенту, потом кодить |
| Приём вебхуков/апдейтов Telegram + отдача баллов клиенту + identity-mapping | `fullstack-guardian` — это одна сквозная задача от Telegram до localStorage, не «бэкенд отдельно, фронт отдельно» |
| Секреты, allowed_updates, проверка, что чужой апдейт не подделать | `security-review` — прогнать перед тем, как включать на боевом канале |
| Автотесты (юнит + интеграционные + e2e) | `test-master` |

Перед стартом — план по протоколу (`redesign-protocol.md#6`):

```text
Mode: Extension
Preserve: economy.js/TIERS/BRANCHES/BETA_OPEN не меняются; схема localStorage
          беты не трогается; contract /api/state и бета-админка не переписываются
Add: приём Telegram-апдейтов о действиях в t.me/rizzoma26, отдельный модуль
     очков (engagement.js), новый эндпоинт, клиентское хранилище баллов
Protected contracts: HMAC-валидация initData, allowed_updates список,
     identity-mapping через существующий users Map в bot.js
Highest-risk change: боту нужны права администратора канала — это ручное
     действие владельца канала, не автоматизируется кодом
Rollback: модуль не пересекается с существующими файлами по данным —
     откат = не запускать новый обработчик апдейтов и не отдавать эндпоинт
```

## 1. Технический факт-чек — прочитать до начала работы

Формулировка задачи говорит «группа t.me/rizzoma26». Проверка перед подготовкой
этого промпта показала другое:

- **t.me/rizzoma26 сейчас — канал** (одностороннее вещание: посты от имени `rizzoma`,
  счётчик просмотров, реакции под постами), **не супергруппа**, где пользователи сами
  пишут сообщения.
- В публичной версии канала (`t.me/s/rizzoma26`) **не обнаружено привязанной группы
  обсуждений** (discussion group) — ни ссылки на неё, ни виджета комментариев в
  разметке страницы. Это не стопроцентная гарантия (виджет мог не отрендериться
  в веб-превью), но по умолчанию считать, что комментариев к постам нет.

Из этого следует: пока это не изменится, «сообщения пользователя в группе» —
события, которых физически не существует. Ловить нечего. Два пути:

| Вариант | Что это даёт | Что нужно сделать |
|---|---|---|
| **A. Работать с тем, что есть** (рекомендация для v1) | реакции на посты, подписка/отписка, бусты канала — этого достаточно для первой версии системы баллов | ничего не менять в канале, только выдать боту права администратора |
| **B. Включить обсуждения** | открывает сообщения, ответы, пересылки внутри группы — более богатый набор действий | **владелец канала вручную** в Telegram-клиенте: Канал → Управление → Обсуждение → создать/привязать группу. Это административное действие в приложении Telegram, Bot API его не выполняет — автоматизировать нечем |

Промпт описывает оба варианта — реализация начинается с варианта A, вариант B
подключается тем же кодом, если/когда группа появится (см. §4).

## 2. Что Bot API может поймать — таблица (проверено по официальной документации)

| Событие | Update-тип | Нужны права администратора? | Доступно сейчас (канал без группы) |
|---|---|---|---|
| Пользователь подписался / отписался от канала | `chat_member` | **да**, и `chat_member` должен быть явно в `allowed_updates` — иначе апдейт не придёт, даже если бот админ | да |
| Реакция на пост | `message_reaction` | **да**, тем же образом — явно в `allowed_updates` | да |
| Агрегированное число реакций без личности пользователя | `message_reaction_count` | нет, приходит всем ботам-участникам | да (но без привязки к пользователю — на баллы не годится, только на витрину «X реакций») |
| Буст канала | `chat_boost` / `removed_chat_boost` | да, аналогично | да |
| Сообщение/ответ в группе обсуждений | `message` (через привязанную супергруппу) | если бот **администратор** группы — получает вообще все сообщения независимо от privacy mode. Если бот обычный участник — только те, что упомянули бота, ответили ему, или после `/setprivacy` → `Disable` у @BotFather | только при варианте B |
| Ответ на опрос в канале/группе | `poll_answer` | нет, но только если сам бот создавал опрос и опрос не анонимный | только если публиковать опросы от имени бота, а не от `rizzoma` |
| Пересылка поста, скриншот, время чтения | — | — | **недоступно в принципе** — Bot API таких данных не отдаёт никому |
| История до того, как бота добавили админом | — | — | **недоступно** — нет метода получить прошлые реакции/подписки задним числом |

Вывод для §4: реалистичный список целевых действий v1 — **подписка на канал**,
**реакция на пост**, **буст канала**. Всё остальное — либо требует ручного шага B,
либо физически недоступно и не должно попадать в ТЗ как «поймать».

## 3. Предусловия — ручные, не автоматизируются кодом

1. Владелец канала добавляет бота **администратором t.me/rizzoma26** (без этого
   `chat_member`/`message_reaction`/`chat_boost` не придут вообще — не вопрос кода).
2. В `bot.js` при старте передать `allowed_updates` явным списком — grammy по
   умолчанию его не расширяет сам:
   ```js
   bot.start({ allowed_updates:
     ['message','chat_member','message_reaction','chat_boost','removed_chat_boost','poll_answer'] });
   ```
   Без этого правки в обработчиках ничего не изменят — апдейты просто не будут
   доезжать до бота, и отладка превратится в гадание.
3. Опционально (вариант B) — привязать группу обсуждений (см. §1) и добавить бота
   администратором уже в неё тоже (права канала и группы разные, выдаются отдельно).

## 4. Целевые действия и баллы — экономика (новый модуль, не `economy.js`)

Отдельный файл `engagement.js` рядом с `economy.js`, тот же архитектурный
паттерн — UMD-обёртка, читается и как `<script>`, и как `require()` в тестах,
чтобы клиент, сервер и юнит-тесты считали баллы по одному коду
(см. `economy.js:1` — обёртка `(function(root, factory){...})`).

Стартовая таблица (числа — черновик, синхронизировать с заказчиком перед боем):

| Действие | Update-тип | Баллы | Ограничение |
|---|---|---|---|
| Подписался на канал | `chat_member` (new status `member`) | 5 | один раз на пользователя, повторная подписка после отписки — 0 |
| Реакция на пост | `message_reaction` | 2 | один раз на пару (пользователь, пост) — смена эмодзи не даёт баллы повторно, снятие реакции не отнимает |
| Буст канала | `chat_boost` | 15 | один раз на буст-слот, `removed_chat_boost` **отменяет** начисление |
| *(вариант B)* Комментарий к посту | `message` в группе обсуждений | 3 | не более N в сутки на пользователя — защита от спама (см. §6) |
| *(вариант B)* Ответ на опрос | `poll_answer` | 1 | один раз на опрос |

`engagement.js` экспортирует:
- `RULES` — таблица выше в виде массива объектов `{key, updateType, points, once}`;
- `pointsFor(ruleKey)` — чистая функция;
- `dedupKey(ruleKey, tgUserId, subjectId)` — детерминированный ключ для антидубля
  (`subjectId` — id поста для реакции, id буста для буста и т.д.);
- `totalFor(events)` — сумма баллов по списку уже принятых событий пользователя.

## 5. Архитектура сбора событий — расширение `bot.js`

Не новый сервис, а обработчики рядом с уже существующими (`bot.on('pre_checkout_query'...)`
на `bot/bot.js:163`, `bot.on('message:successful_payment'...)` на `bot/bot.js:178`):

```js
bot.on('chat_member', ctx => { /* new_chat_member.status, tg id */ });
bot.on('message_reaction', ctx => { /* new_reaction[], old_reaction[], from */ });
bot.on('chat_boost', ctx => { /* boost.source.user, boost.boost_id */ });
bot.on('removed_chat_boost', ctx => { /* откат начисления по boost_id */ });
```

- Все обработчики фильтруют по `ctx.chat.id === CHANNEL_ID` (новая переменная
  окружения `CHANNEL_ID`, значение — числовой id канала, не `@username`; узнаётся
  через `getChat` один раз при настройке) — иначе бот случайно начнёт считать баллы
  за реакции в чужих чатах, если его туда позовут.
- Личность сопоставляется тем же способом, что и везде в проекте — через
  существующий `users` Map и `upsert()` (`bot/bot.js:73`), по `tg id`. Никакой
  второй системы идентификации не заводим: пользователь в дереве узлов и
  пользователь в канале — один и тот же `upsert(tg)`.
- Событие проходит дедуп по `dedupKey()` из `engagement.js` через новый `Set`/`Map`
  в памяти (`engagementLog`), тем же «демо-уровнем», что и остальное хранилище бота
  (`users`/`codes`/`payments` — простые структуры в памяти, без БД, см.
  `README.md` → «Что заменить перед боевым запуском»).
- Новый эндпоинт `/api/engagement` — `{initData}` → `{points, events:[...]}`, по
  образцу `/api/state` (`bot/bot.js:262`): тот же `auth()`, тот же паттерн ответа.

## 6. Антифрод и дедупликация

- Один и тот же `dedupKey` не начисляет баллы дважды — реакция toggle
  (поставил → снял → поставил) считается один раз, а не на каждое нажатие.
- `removed_chat_boost` не просто игнорируется, а **списывает** ранее начисленные
  баллы за конкретный `boost_id` — иначе снятие буста можно повторять ради фарма.
- Сообщения от самого бота и служебные апдейты (`ctx.from.is_bot`) исключаются
  из подсчёта сразу на входе в обработчик.
- Вариант B (комментарии): суточный потолок на пользователя (например, 5 засчитанных
  комментариев в сутки) — иначе бот, флудящий в чате, зарабатывает бесконечно.
- Ничего из этого не «защита от мошенничества уровня прод» — как и остальная
  экономика беты, это демо-уровень: журнал в памяти, переживёт рестарт только если
  добавить БД (см. §8). Явно писать это в README нового модуля, тем же тоном, что
  и для остальной беты — не выдавать демо за прод-защиту.

## 7. Хранение баллов «локально» — что это значит технически

Формулировка задачи — «баллы хранятся локально (в демо-версии)» — реализуется так:

- Сервер **не** является хранилищем баллов «навсегда»: он только принимает
  Telegram-апдейты, дедуплицирует и умеет ответить текущей суммой по запросу
  клиента. Рестарт процесса стирает журнал — так же, как сейчас стирается `users`.
- Источник правды для пользователя — **клиент**: новый ключ `localStorage`,
  например `rizzoma_engagement`, по образцу существующих `K_CLAIMS`/`K_BETA`
  (`index.html:682`, `index.html:812`). Клиент при старте (там же, где сейчас
  вызывается `/api/state` — `index.html` секция запуска) дополнительно дёргает
  `/api/engagement` и сохраняет ответ в этот ключ.
- **Важное архитектурное решение, требующее подтверждения**: включать ли новый
  ключ в `CLOUD_KEYS` (`index.html:684`) — то есть синхронизировать баллы между
  устройствами пользователя через Telegram `CloudStorage`, как `rizzoma_claims`,
  или оставить чисто локальным на одном устройстве/браузере, как `rizzoma_beta`
  (`index.html:812` сознательно **не** в `CLOUD_KEYS`). Раз в задаче написано
  «хранятся локально» буквально — по умолчанию **не** добавлять в `CLOUD_KEYS`
  (поведение как у `rizzoma_beta`), но явно спросить/зафиксировать это решение
  перед реализацией, а не молча выбрать один вариант.

## 8. Явно вне объёма этой задачи

- **Не** трогать `TIERS`/`BRANCHES`/`BETA_OPEN` и логику дерева скиллов — баллы за
  активность в канале не конвертируются в узлы дерева и не меняют экономику
  рефералов. Если в будущем понадобится мост «баллы → скидка/скилл» — это
  отдельный промпт после того, как эта система обкатана сама по себе.
  Не изобретать этот мост по собственной инициативе внутри текущей задачи.
- **Не** проектировать полноценный игровой UI под баллы (анимации, окна, «победные»
  эффекты по аналогии с деревом узлов). Достаточно компактного, честного отображения
  суммы — например, строкой во вкладке «Свои» или в окне «i» (`renderInfo()`,
  `index.html`), без новой визуальной системы. Если после показа заказчику
  понадобится больше — это следующий промпт, не эта задача.
- **Не** переводить бота на webhook-режим ради этой задачи: `bot.start()` (long
  polling, `bot/bot.js:393`) получает те же типы апдейтов, что и вебхук, если
  указан `allowed_updates` (§3) — менять транспорт незачем.

## 9. Минимальный UI

Один компактный, доступный без активации узла блок (баллы за подписку/реакции
не должны требовать «сначала стать узлом дерева» — это разные системы):

- вкладка «Свои» (`index.html`, `renderCrew()`) или окно «i» — строка вида
  «Активность в канале: N баллов · M событий»;
- если `/api/engagement` недоступен (бэкенд не настроен или бот не админ канала) —
  честный текст по образцу существующих «источник: демо» (`crewGate()`,
  `index.html`), а не пустой блок и не ошибка в консоли.

## 10. Автотесты — обязательная часть задачи

### 10.1 Юнит-тесты (`tests/engagement.test.mjs`, `node --test`)

По образцу `tests/economy.test.mjs` — чистые функции без сети и без Telegram:

- `pointsFor()`/`totalFor()` считают правильно по таблице `RULES`;
- `dedupKey()` для одинаковых входов даёт одинаковый ключ, для разных
  пользователей/постов/бустов — разные;
- повторное применение одного и того же события к журналу не удваивает сумму;
- `removed_chat_boost` вычитает ровно то, что было начислено тем же `boost_id`,
  а не фиксированную сумму (защита от рассинхрона, если правила поменяются).

### 10.2 Интеграционные тесты бэкенда (без реального Telegram)

grammy позволяет скормить боту синтетический `Update` напрямую —
`await bot.handleUpdate(update)` — без сети и без реального сервера Telegram.
Тесты собирают реальные по форме JSON-объекты (по структуре из Bot API:
`message_reaction`, `chat_member`, `chat_boost`) и прогоняют через бота:

- реакция от нового пользователя → баллы начислены, событие в `/api/engagement`;
- та же реакция вторым апдейтом (Telegram иногда шлёт повторы) → баллы не удвоились;
- `chat_member` не из `CHANNEL_ID` (апдейт из постороннего чата) → игнорируется,
  ничего не создаётся;
- `message_reaction` от `ctx.from.is_bot === true` → игнорируется;
- `chat_boost` → баллы начислены; следующий `removed_chat_boost` с тем же
  `boost_id` → баллы списаны, повторный `removed_chat_boost` не списывает второй раз;
- `/api/engagement` с невалидной `initData` → `401`, как у остальных эндпоинтов
  (проверить тем же способом, что уже есть для `/api/state` — см. историю проверки
  HMAC в этом же проекте, где нашли и закрыли баг с обрезанием `hash`);
- **allowed_updates не забыт**: отдельный тест проверяет, что при старте бота
  передаётся ожидаемый список типов (например, экспортировать константу
  `ALLOWED_UPDATES` из `bot.js` и свериться с ней в тесте) — иначе в проде легко
  тихо потерять типы апдейтов без единого упавшего теста.

### 10.3 E2E (Playwright, по образцу `tests/e2e/beta.spec.mjs`/`helpers.mjs`)

`/api/engagement` мокается через `page.route()` тем же способом, каким сейчас
мокаются `telegram-web-app.js`/`config.js` (`tests/e2e/helpers.mjs`):

- клиент показывает сумму баллов и число событий из ответа сервера;
- при ответе `apiBase` не настроен / бот не админ — честный текст, а не пустой блок
  и не необработанное исключение в консоли (проверить `read_console_messages`-эквивалент
  через отсутствие ошибок в `page.on('pageerror', …)`);
- баллы не показываются как часть дерева узлов и не блокируют покупку билета —
  сценарии §10.3 не должны задевать существующие тесты беты (прогнать полный
  `npm run test:e2e` после добавления — старые 11 тестов обязаны остаться зелёными).

### 10.4 Ручной приёмочный прогон (не CI — настоящего канала в тестах нет)

По аналогии со сценарием двух аккаунтов из `beta-launch-prompt.md` §5.3:
1. Добавить бота администратором в тестовый канал-дублёр (не боевой `rizzoma26`,
   пока сценарий не обкатан).
2. Вторым Telegram-аккаунтом подписаться и поставить реакцию на пост.
3. Проверить в бэкенд-логе/`/api/engagement`, что событие дошло и баллы начислены,
   в приложении — что баллы отображаются.
4. Только после чистого прогона — выдавать боту права администратора на боевом
   `t.me/rizzoma26`.

### 10.5 CI

- `package.json` → `"test": "node --test tests/economy.test.mjs"` сейчас указывает
  **на один конкретный файл** — добавление `tests/engagement.test.mjs` само по себе
  не запустится в CI, если не поменять скрипт на что-то вроде
  `"test": "node --test tests/*.test.mjs"`. Без этой правки новые юнит-тесты будут
  зелёными локально и невидимыми в `.github/workflows/ci.yml`, что хуже, чем их
  отсутствие — создаёт ложное чувство покрытия. Проверить это в первую очередь.
- Новый e2e-файл в `tests/e2e/*.spec.mjs` подхватывается существующим
  `playwright.config.mjs` (`testMatch: '**/*.spec.mjs'`) автоматически.

## 11. Секреты и переменные окружения

Добавить в `bot/.env.example` (существующий файл, паттерн не менять):

```
# Числовой id канала (не @username) — узнаётся через getChat один раз при
# настройке. Без него бот будет считать баллы за реакции в любом чужом чате,
# куда его позовут.
CHANNEL_ID=

# Тот же BOT_TOKEN, отдельного токена под эту задачу не нужно — это тот же бот
```

Секретов, специфичных для этой задачи, кроме уже существующего `BOT_TOKEN`, нет —
`CHANNEL_ID` не секрет, но должен настраиваться через env, а не быть зашит в код
(тот же принцип, что и `ADMIN_TG_IDS`).

## 12. Критерии приёмки

1. `allowed_updates` явно перечислен при старте бота — задокументировано и
   покрыто тестом (§10.2), не полагается на дефолт.
2. Подписка на канал, реакция на пост и буст канала (в тестовом канале-дублёре,
   §10.4) корректно превращаются в баллы; повторные/дублирующиеся апдейты не
   удваивают сумму; снятие буста списывает баллы за него.
3. Апдейты из чужих чатов и от ботов игнорируются, не роняют сервер.
4. `/api/engagement` отвечает `401` на невалидную `initData`, как остальные
   эндпоинты; при отсутствии `apiBase`/прав администратора клиент показывает
   честный текст, не пустой блок и не ошибку в консоли.
5. Баллы хранятся в `localStorage` клиента отдельным ключом; решение о включении
   в `CLOUD_KEYS` зафиксировано явно (§7), а не выбрано молча.
6. Дерево узлов, `TIERS`/`BRANCHES`/`BETA_OPEN`, покупка билета и вся механика
   беты не изменились — полный прогон `npm test` и `npm run test:e2e` зелёный,
   включая все существующие тесты, не только новые.
7. `package.json` подхватывает новый тестовый файл в CI (§10.5), проверено
   прогоном workflow, а не только локально.
8. README нового модуля честно описывает демо-уровень (журнал в памяти, не
   переживает рестарт бота) — тем же тоном, что остальная документация беты,
   без выдачи демо за защищённую от фрода систему.
